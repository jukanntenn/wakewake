# RFC: Cloudflare edge topology — real client IP, origin lockdown, cache semantics, and SSE backstops

Status: proposed

English | [中文](2026-08-23-cloudflare-edge-topology.zh.md)

## Problem

Prod launches with every request proxied through Cloudflare's Free plan (orange-cloud DNS, Full-strict with an Origin Certificate; a host systemd Caddy gateway on `:443` is the only exposed listener on the shared VPS, reverse-proxying to the loopback-only container — Free-plan edge caching exists only on proxied port 443, so the origin answers on 443 rather than on a rewritten high port). Four defects came with that topology. First, the client-IP chain was wrong end to end: with Caddy's defaults the backend's "client IP" was the Cloudflare edge address (Caddy overwrites X-Forwarded-For with the untrusted peer), collapsing per-IP governor buckets into per-PoP shared buckets — a load-test finding (R3) — and writing Cloudflare edge IPs into `login_events.ip_address`; the R3 remedy (per-handler `trusted_proxies` in `routes.caddy`) fixed the shared buckets but switched Caddy into append-mode XFF, where the leftmost entry is visitor-supplied and forgeable, so the backend's leftmost-XFF derivation became an attack on rate limiting and audit data. Second, the origin accepted direct connections: anyone holding the VPS IP could bypass every edge protection (rate limiting, WAF, caching) by connecting straight to Caddy. Third, HTML responses carried no `Cache-Control`, so Cloudflare's Free plan injects its default Browser Cache TTL (4 hours) into browser responses — stale dashboards after releases — while the immutable assets were the only thing the edge could usefully cache. Fourth, observability and abuse backstops were missing: the backend's default `TraceLayer` span is DEBUG-level with no IP (invisible at the production `log.level=info`), Caddy logged edge IPs as `client_ip`, nothing carried `cf-ray` for correlating with Cloudflare's sampled Security Events, and the SSE endpoint had a device-quota bound on connection cardinality but no global cap.

## Proposal

The authoritative client IP travels in a dedicated header, not the XFF chain. Cloudflare always sends `CF-Connecting-IP` (exactly one IP, the connecting visitor); the XFF chain behind CF is append-mode and its leftmost entry is forgeable. A new `[server].client_ip_header` (env `WAKEWAKE_SERVER__CLIENT_IP_HEADER`, unset by default) names that header; `util::client_ip_from_headers` reads it first, then falls back to the existing XFF/X-Real-IP/TCP-peer derivation, and every consumer shares this one function — the governor `ClientIpExtractor`, the login audit (`login_events.ip_address`), and the new TraceLayer span. Unset, all non-CF environments keep today's semantics byte-for-byte. This knob is safe only when the access layer admits nothing but trusted proxies, so it ships welded to the origin lockdown: the prod host runs a systemd Caddy gateway on `:443` that terminates TLS with the Origin Certificate and whose site block (`wakewake.caddy.j2`, rendered by `deploy.yml` from `cloudflare_cidrs` in `group_vars/prod/env.yml`, source of truth `cloudflare.com/ips`) answers 403 to every non-Cloudflare source and reverse-proxies to the loopback-only container port; `CF-Connecting-IP` passes through the gateway untouched to the backend. The backend `http_request` span is where the visitor IP and `cf-ray` are canonically recorded — the gateway's own access log keeps its default shape. The backend setting rides `config.toml.j2` via `server_client_ip_header` and is rendered only when defined — prod sets it, other environments never do.

Caching semantics become explicit at the origin: `routes.caddy` already sends `Cache-Control: public, max-age=31536000, immutable` for `/_next/static/*` and, as of this change set, `public, max-age=0, must-revalidate` for the HTML shell — the browser revalidates on every navigation (ETag 304 against `file_server`) and Cloudflare's 4-hour default Browser Cache TTL no longer applies to responses that carry their own directive; a short-edge-TTL Cache Rule for the shell (referenced by the routes.caddy comment) is the optional bandwidth offload on top. Observability and backstops complete the set: the backend TraceLayer span becomes INFO-level `http_request` carrying `client_ip` (same derivation), `cf_ray`, method, and URI with an INFO response event (status + duration), and a global SSE connection cap `[server].max_sse_connections` (default 2000, 0 = unlimited) rejects further SSE handshakes with 503 SERVICE_UNAVAILABLE — connection cardinality stays bounded by paired agents (same-agent reconnects replace, never stack), and the cap is the total-flood backstop; `sse_connections_active` already exports the gauge to watch it against. The Free-plan console posture (one rate-limiting rule on `/api/v1/auth/*`, Bot Fight Mode off because it challenges non-browser clients like the agent SSE channel, Under Attack as the emergency switch, origin error-rate alerts) and the post-launch verification runbook live in [cloudflare.md](../../../../devops/cloudflare.md).

One sync duty this creates: the Cloudflare CIDR set now appears in three places that must move together — the two `trusted_proxies` lines in `docker/caddy/routes.caddy` (image-baked, all environments) and `cloudflare_cidrs` in `group_vars/prod/env.yml` (the prod gateway guard). And one coupling that must never be split: `trusted_proxies` (routes.caddy) without `client_ip_header` on the backend leaves the leftmost-XFF forgeability open; `client_ip_header` without the gateway's `remote_ip` guard lets a direct connector forge the authoritative header itself. Removing either side is a security decision, not cleanup.

## Alternatives considered

**Override XFF at Caddy (`header_up X-Forwarded-For {http.request.header.CF-Connecting-IP}`)** — Cloudflare's own documented Caddy recipe. Lost: it would have to live in `routes.caddy`, the routing truth shared by all four TLS variants, either dragging CF-specific behavior into self-deploy/local/e2e or demanding a snippet-parameterization mechanism Caddyfiles don't naturally offer; the config-driven backend header keeps `routes.caddy` untouched and the Rust side unit-testable.

**Parse XFF right-to-left, skipping trusted proxies (Caddy's `trusted_proxies_strict` logic).** Lost: it requires every proxy hop's ranges to be enumerated and stays correct only while the chain is exactly as modeled; a single authoritative header is one fact instead of an inference over a chain whose prefix is attacker-controlled.

**Do it all at the Cloudflare edge (WAF, rate limiting, Under Attack) and touch nothing repo-side.** Lost: the Free plan allows one rate-limiting rule with fixed 10 s windows and documents that excess requests still reach the origin; per-IP governor limits, PoW, lockout, and quotas are the precise layer and depend on a correct client IP, which the edge cannot restore by itself.

**A Caddy rate-limiting module for origin-side throttling.** Lost: the official release binary carries no such plugin — adopting one means an xcaddy-built custom image for every environment, and the CF rule plus governor layers already cover the same threat.

**A per-user SSE connection cap instead of a global one.** Lost: cardinality per user is already the device quota (one live channel per paired agent, reconnects replace), so the per-user cap is the quota wearing a second name; the missing piece was the total-flood backstop, which one global number provides.

## Acceptance criteria

- Unit tests cover the header matrix in `util.rs` and `rate_limit.rs`: authoritative header beats spoofed-XFF chains, missing/garbage header falls back to XFF, unset preference keeps XFF semantics, `trust_proxy=false` ignores all headers; SSE cap tests in `routes/sse.rs` cover zero-unlimited, reject-at-limit, and same-agent reconnect not stacking.
- Rendered prod config: `config.toml` carries `client_ip_header = "CF-Connecting-IP"`; test/staging/self-deploy configs carry no such key and behave as before.
- The runbook in [cloudflare.md](../../../../devops/cloudflare.md) §8 passes against production: spoofed XFF leaves `login_events.ip_address` at the real visitor IP, direct VPS-IP connections get 403, immutable assets show MISS→HIT with growing `Age` and preserved origin `Cache-Control`, the HTML shell shows the short-TTL edge behavior with `max-age=0, must-revalidate`, API responses are DYNAMIC without `Age`, and an SSE connection held open emits `: ping` every 30 s.
- Backend `http_request` spans appear at `log.level=info` with `client_ip` (derived from `CF-Connecting-IP`, which the host gateway passes through untouched) and `cf_ray`; the gateway site block 403s any direct non-CF connection before it reaches the container.
- `doc_sync.py` runs green over the touched documentation corpus; `cargo clippy` and `cargo test` pass for `wakewake-server`.

## Risks

The Cloudflare CIDR list can drift from `cloudflare.com/ips`; the three copies (two in `routes.caddy`, one in `env.yml`) make drift a silent misfire — a stale list rejects legitimate CF traffic at the guard (403) or trusts ranges CF no longer uses, and the mitigation is the documented quarterly review, which the env.yml comment states but nothing enforces. The `trusted_proxies` ↔ `client_ip_header` coupling is only as durable as the WRFC that warns about it; a future cleanup that removes the backend header "for simplicity" reopens leftmost-XFF forgery in exactly the environments that trust proxies. `max_sse_connections` at 503 shares its error code with mailer-disabled and other unavailability states, so an agent cannot distinguish capacity exhaustion from breakage — acceptable because both call for backoff, but operators reading dashboards must know the cap logs a warning per rejection. The HTML shell's `must-revalidate` turns every navigation into a conditional request to the origin (304s, small but nonzero on a 3 Mbps link); if that ever measures hot, the Cache-Rule edge TTL — not a looser browser directive — is the designed relief valve. Free-plan behavior itself is the outermost risk: the console posture documented in cloudflare.md is enforced by no gate in this repo, so console drift (a toggled Bot Fight Mode, a deleted rate-limiting rule) degrades silently until the §8 runbook is re-run.
