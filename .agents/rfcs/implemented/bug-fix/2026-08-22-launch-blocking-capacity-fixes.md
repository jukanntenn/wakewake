# RFC: Launch-blocking capacity fixes — per-IP global rate limit, SSE backoff reset, and FD ceilings

Status: implemented

English | [中文](2026-08-22-launch-blocking-capacity-fixes.zh.md)

## Problem

The pre-launch capacity review (target: 2c/2g/3Mbps VPS behind free Cloudflare) re-read the hot paths with production traffic in mind and found three defects that bite at trivial scale, none of them hardware limits. First, the fallback rate limiter in [middleware/rate_limit.rs](../../../../backend/crates/server/src/middleware/rate_limit.rs) keyed on `Global` — one bucket of 120 req/min shared by the entire server, every route merged into the API router: the dashboard polls at ≈40 req/min per open tab (`useDevices` 3s while syncing, `useAgents` 5s, `useIntegrations` 3s, `useWakes` 10s), so about three concurrent pages would trip 429s for everyone; agent `/agents/self/sync` calls and even the Docker healthcheck (10s) plus the Caddy upstream probe (10s) drew from the same 12-req/min-starved bucket. The load suite had `WAKEWAKE_RATE_LIMIT__DISABLED=true` baked into its compose override, so no test could ever see this. Second, the agent's reconnect backoff could never reset: `connect_and_run` returned only `Unauthorized`/`Disconnected`, the `Outcome::Connected` arm in [agent main.rs](../../../../backend/crates/agent/src/main.rs) was dead code, so `backoff.reset()` was unreachable — after weeks of healthy connections a single network blip retried at a grown interval, and the counter ratcheted monotonically toward the 300s cap for the process lifetime. Third, neither [docker/docker-compose.yml](../../../../docker/docker-compose.yml) nor the ansible template set `ulimits.nofile`, leaving SSE capacity at the mercy of the daemon default (soft 1024 on common hosts — about a thousand connections); the load override had to raise it to run 5k connections, which is itself the evidence production needed it too.

## Decision

The global fallback limiter is per-client-IP at 600 req/min — same `ClientIpExtractor` and `trust_proxy` semantics as the auth limiter, `max_keys` 50,000 with a 1-minute GC interval. Fifteen times one dashboard's draw, unreachable by legitimate users, still a hard ceiling for a single-IP flood; per-user/per-agent budgets are unchanged. Health routes (`/health`, `/health/maintenance`, `/version`) are merged after the fallback layer is applied, exempting them: infrastructure probes must never consume user-facing quota, and the healthcheck must answer even while the limiter is misbehaving. The agent's `connect_and_run` now tracks whether the stream ever delivered bytes; a drop after data was received returns `Outcome::Connected`, and the main loop responds by resetting the backoff and retrying at base+jitter (2.5–7.5s) — a single blip heals in ~5s, and a server-restart storm spreads over the ±50% jitter window by design. Failures before any byte arrives (connect error, non-200, instant EOF) keep ratcheting the backoff. Both production compose files (self-deploy and ansible template) set `ulimits.nofile` soft/hard 1,048,576, matching the load-test override.

## Alternatives considered

**Raise the Global bucket to a large constant (e.g. 20k/min).** Lost: it keeps punishing aggregate traffic — a legitimate traffic surge and a flood are the same event to a global key — and the number is unprincipled; per-IP is the granularity at which the abuse model (one bad client) and the legitimate model (many modest clients) separate.

**Drop the fallback limiter entirely, keep auth-only limits.** Lost: the fallback is the only layer covering JWT-protected and agent M2M routes; removing it leaves those endpoints with no rate ceiling at all, and Cloudflare's free tier offers exactly one rate-limiting rule — spend it on `/auth/login` (the bcrypt CPU wall), not on generic coverage the app can provide itself.

**Exempt health via an axum matcher inside the layer.** Lost: `Router::layer` applies to routes already merged, so merging health after the layer is the idiomatic zero-machinery exemption; a matcher re-derives route identity the router already encodes.

**Reset the backoff the moment the HTTP 200 arrives (not after first byte).** Lost: a 200 followed by an immediate stream error is a half-open failure mode, and retrying it at base rate converts a flapping upstream into a connect storm; requiring delivered bytes means only connections that were actually healthy earn the reset.

**Keep retrying `Connected` drops with zero delay.** Lost: a server restart would then face the full agent fleet reconnecting in the same instant; the base+jitter sleep (2.5–7.5s spread) is the storm-protection the backoff design exists for, and reset restores the *interval*, not the absence of one.

**Set the FD limit only on the VPS host (systemd override).** Lost: compose `ulimits` travels with the deployment definition, is exercised by every environment including the load rig, and does not depend on an undocumented host-side step surviving the next VPS rebuild.

## Consequences

`cargo clippy` and the full workspace test suite (real PG) pass; e2e and integration suites run with `rate_limit.disabled=true` so their behavior is unchanged by the quota/key change, and the per-IP semantics are exercised going forward by the load suite's rate-limit-on profile (the load override now must be toggled deliberately when headroom — not correctness — is under test). The 429 surface keeps the JSON envelope plus `Retry-After` from the shared error handler. The per-IP keying depends on correct client-IP propagation, and the first full-scale load-matrix run was exactly that verification — and it failed: Caddy (≥2.7 security behavior) rewrites the inbound X-Forwarded-For of untrusted sources to the immediate peer IP, so every client behind a proxy collapses into one rate-limit bucket (in production, one Cloudflare edge IP per user population — a launch-blocking storm of 429s); `docker/caddy/routes.caddy` now declares `trusted_proxies static` (all Cloudflare ranges plus RFC1918, overridable via the `TRUSTED_PROXIES` env) on both reverse-proxy blocks, which restores first-hop keying for the CF→Caddy chain and for the load rig's per-VU X-Forwarded-For; `max_keys` 50,000 bounds the limiter's memory under IP-spoofed floods at the cost of evicting legitimate keys under that same flood, which is the intended degradation; and the `Connected`-reset behavior makes reconnect storms after restarts denser by design (all agents at base+jitter instead of staggered grown intervals) — the load suite's R3 reconnect-storm scenario exists to measure exactly that wave against the 3Mbps uplink, and the state-push token bucket proposed in the local perf-est notes remains unbuilt and is the documented mitigation if R3 measures saturation beyond tolerance.
